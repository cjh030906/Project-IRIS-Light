### 1.3 Ready 계약 (설계상 이중 기준)

| 기준 | 범위 | 용도 |
|------|------|------|
| `verify_core_quick` | Ollama 응답 · usable 모델 · Hermes `/health`(+ready) | `core_ready` / 부팅 게이트 |
| `verify_core` | quick + 채팅 auth probe + MCP stdio | 설정「검사」·`core_smoke` |

**설계상 포함하지 않음:** 실제 사용자 채팅에서 Hermes가 tools를 강제할 때 모델이 도구를 지원하는지.

### 1.4 자동·우회 원칙 (설계)

```
needs_user + can_install → 클릭 없이 install (auto_install)
install 후에도 needs_user → 사용자에게 넘김 (재자동설치 금지)
Hermes 공식 실패(448/rc≠0) → _install_hermes_bypass (시스템 Python + pip)
prefer_bypass / last_error(bypass·448) → 이후 공식 생략·우회 직행
```

## 6. 종합 판정

1. **「설치하고 연결되는가」** — 본 환경 기준으로 **예.** Core 10·헬스·MCP·클라우드 경로는 설계 흐름대로 맞춰짐. 오류 시 우회(Hermes)·키 rotate·gateway 재기동 코드 경로도 구현되어 있음.
2. **「Ready면 채팅까지 되는가」** — **아니오(조건부).** 프로토콜이 고른/승인한 로컬 모델이 도구 미지원이면, 사용자 체감 채팅은 실패한다. 이는 구현 누락이라기보다 **Ready 계약이 실채팅(tools)을 포함하지 않는 설계 한계**이며, 현재 기본 로컬 모델과 Hermes 도구 강제가 충돌한다.
3. **품질 게이트** — 제품 단위테스트는 통과하나, **패키지 자체검증 스크립트가 깨져 있어** CI/수동 `python -m iris.system.setup_protocol` 신뢰도가 떨어진다.
