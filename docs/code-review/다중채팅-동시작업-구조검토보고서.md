# 다중 채팅 동시 작업 구조 검토 보고서


| 항목      | 내용                                                      |
| ------- | ------------------------------------------------------- |
| 문서 번호   | IRIS-REV-2026-0930-02                                   |
| 작성일     | 2026-09-30                                              |
| 대상      | Iris Light 메인 채팅·도구 실행                                  |
| 목적      | 어떤 채팅에서든 대화, IDE, 서류, 자료 조사를 동시에 수행하도록 바꿀 때의 구조 수정안과 손익 |
| 조사 범위   | Iris 소스, Cursor·OpenAI·Anthropic 공개 문서, ReAct 논문        |
| 하지 않은 일 | 제품 바이너리 역공학, 비공개 프로토콜 추정                                |


공개 문서가 제품 내부 스케줄러까지 적지 않은 부분은 논문의 에이전트 루프와 공개된 세션·격리 모델로 메웠다. Cursor·GPT·Claude의 실행 파일은 열지 않았다.

---



## 1. 결론

지금 구조로는 불가능하다. 대화 기록은 채팅마다 저장되지만, 모델 호출과 도구 실행은 창 전체에서 하나다. 다른 채팅을 열면 진행 중 작업이 취소된다.

목표 동작은 가능하다. 공통 패턴은 「채팅 하나 = 세션 하나 = 그 세션 안의 도구 루프」이다. 파일을 고치는 작업은 세션만 나누면 부족하고, 작업 사본(Git worktree 또는 동등한 격리)이 있어야 서로 덮어쓰지 않는다. 글 조사·위키 요약처럼 서로 다른 대상을 읽는 작업은 세션 분리만으로 병렬이 된다.

권고는 한 번에 전면 교체하지 않고, 세션 실행을 먼저 나누고, 파일·IDE 쓰기는 잠금 또는 worktree로 나중에 여는 것이다.

## 3. 현재 Iris

메인 채팅은 창 하나, 실행 슬롯 하나다.


| 구성  | 현재                                                                              |
| --- | ------------------------------------------------------------------------------- |
| 기록  | `ChatSession`이 대화 id와 히스토리를 DB에 나눈다. 이 부분은 이미 채팅별이다.                            |
| 실행  | `ChatTurnGate.busy`, `UserTurnDispatcher`, `_chat_worker`가 각 하나다.               |
| 전환  | `_load_conversation`은 생성 중이면 `request_cancel`하고 `대화 전환으로 응답을 중단했습니다.`를 남긴다.     |
| 입력  | 생성 중 전송 버튼은 정지다. 키보드 전송은 대화 id를 큐에 싣지 않는다.                                      |
| 모델  | `settings.ollama_model`이 하나다. Hermes `set_inference_model`은 런타임 기본 모델을 통째로 바꾼다. |
| 도구  | IDE, 파일 쓰기, 위키, 긴 작업 이어하기가 창 전역 상태다.                                            |
| 예외  | 메일·캘린더 패널은 워커가 따로 있으나, 채팅 목록의 다른 대화가 아니다. 그 화면일 때 메인 턴을 끝내고 넘긴다.                |


그래서 자료 조사 중이어도 다른 채팅의 IDE 작업이 그 조사를 끊는다. 저장이 나뉜 것과 실행이 나뉜 것은 다르다.

## 4. 목표 구조

채팅은 세션이다. 세션은 자기 기록, 자기 모델, 자기 도구 루프를 가진다. 화면은 그중 하나만 크게 보여주고, 나머지는 백그라운드에서 같은 루프를 돈다.

```text
채팅 A ── 세션 A ── 루프(모델, 도구, 기록 A)
채팅 B ── 세션 B ── 루프(모델, 도구, 기록 B)
화면은 포그라운드 세션만 그린다.
파일 쓰기는 세션이 빌린 작업 사본 또는 경로 잠금 안에서만 한다.
```

도구 종류별 격리:


| 작업                     | 필요한 격리                              |
| ---------------------- | ----------------------------------- |
| 대화, 자료 조사, 서로 다른 문서 읽기 | 세션 기록과 루프만 분리                       |
| 위키에 서로 다른 노트 쓰기        | 경로 잠금. 같은 노트는 한 세션만                 |
| IDE, 같은 저장소 수정         | Git worktree 또는 동등한 사본. 본 트리는 한 세션만 |
| 터미널 명령                 | 세션별 작업 디렉터리. 같은 디렉터리의 동시 실행은 금지     |


Cursor 공개 문서의 worktree, OpenAI의 conversation id, Claude의 session/thread가 같은 역할이다. ReAct 논문의 궤적은 세션 안에 있고, 궤적끼리 합치지 않는다.

---



## 5. Iris 수정 순서

1. **세션 실행 객체.** 대화 id마다 워커, 진행 플래그, 이어하기 횟수, 부분 응답을 둔다. `ChatTurnGate`와 `_chat_worker` 단일 필드를 맵으로 바꾼다. 지금 보고 있지 않은 세션의 토큰은 그 대화 DB에만 붙인다.
2. **전환은 화면만 바꾼다.** `_load_conversation`에서 `conversation_switch` 취소를 뺀다. 포그라운드가 바뀌어도 백그라운드 루프는 `request_cancel`하지 않는다.
3. **입력은 세션으로 보낸다.** 키보드 전송에 대화 id를 싣는다. 생성 중인 채팅의 버튼은 그 채팅의 정지이고, 다른 채팅의 전송을 막지 않는다.
4. **모델은 요청 단위.** Hermes가 켜져 있으면 `set_inference_model`로 전역 기본 모델을 바꾸지 않고, 그 요청의 모델만 싣는다. 같은 모델만 병렬로 쓸 1단계에서는 이 항을 미룰 수 있다.
5. **쓰기 도구는 빌림.** IDE·`project.write_file`·터미널은 세션이 잠금을 얻었을 때만 실행한다. 잠금이 없으면 그 세션은 기다리고, 다른 세션의 읽기·조사는 계속된다. worktree는 그 다음 단계다.
6. **상한.** 동시 루프는 2 또는 3으로 시작한다. 로컬 Ollama는 한 모델 서버를 나눠 쓰므로 무제한 병렬은 처리량만 떨어뜨린다.

메일·캘린더 패널의 별도 워커는 이 세션 맵에 흡수할 대상이지, 병렬 채팅의 본보기가 아니다.

## 6. 손익



### 장점

- 한 채팅의 조사·서류가 끝나기 전에 다른 채팅에서 IDE나 다른 조사를 시킬 수 있다.
- 채팅을 옮겨도 진행 중 답이 취소되지 않는다.
- 기록 저장은 이미 대화별이라, 실행만 세션에 붙이면 된다.
- 파일 사본을 쓰면 Cursor와 같이 본 작업 트리를 더럽히지 않고 코딩 작업을 겹칠 수 있다.



### 단점과 리스크

- Hermes 전역 모델을 그대로 두면, 모델이 다른 두 채팅이 서로의 요청을 덮어쓴다.
- 잠금 없이 IDE·파일 쓰기를 열면 두 세션이 같은 파일을 동시에 고친다. Claude 공개 문서도 스레드 기록은 나누면서 샌드박스 파일은 공유할 수 있다고 적는다. Iris는 그 공유가 기본이다.
- 로컬 GPU·Ollama는 루프를 늘려도 처리가 직렬에 가깝다. 병렬은 대기 취소가 없어지는 이득이지, 두 배 속도가 아니다.
- 클라우드 세션·주간 한도는 채팅 수만큼 빨리 소모된다.
- 백그라운드 세션의 도구 승인 창이 포그라운드 작업을 가릴 수 있다. 승인은 그 세션에 속해야 한다.
- 음성·전역 마이크는 여전히 하나다. 말을 어느 채팅에 넣을지 규칙을 정하지 않으면 백그라운드 세션으로 새지 않는다.
- worktree를 성급히 넣으면 의존성 설치와 결과 병합이 새 장애가 된다. Cursor 문서도 결과를 본 트리로 되돌리는 단계를 따로 둔다.

---



## 7. 권고

1단계는 세션별 루프와 전환 시 취소 제거, 동시 2개, 파일·IDE 쓰기는 잠금 하나다. 이 단계만으로 조사와 서류는 채팅마다 동시에 가고, 코딩은 한 채팅만 쓴다.

2단계는 요청 단위 모델이다. 채팅마다 다른 모델을 쓸 때 필요하다.

3단계는 코딩 병렬이다. Git worktree로 세션별 사본을 만들고, 끝나면 사용자가 본 트리로 가져온다. 그 전에 자동 병합은 넣지 않는다.

---



## 8. 바꾸는 층과 프레임워크

프레임워크를 바꾸지 않는다. Hermes를 LangGraph·AutoGen·Claude Agent SDK 같은 다른 에이전트 런타임으로 갈아끼우는 일이 아니다. Hermes 프로세스, `iris/system/hermes_gateway.py`의 기동·헬스, `iris/core`(파서·인용·활동 기록)도 이 변경의 본체가 아니다.

막는 것은 아이리스가 창 하나에 실행 슬롯을 하나만 둔 부분이다.


| 층                | 이 변경에서                                                                                                                                                   |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 아이리스 채팅 실행       | 본체. `ChatTurnGate`, `UserTurnDispatcher`, `MainWindow._chat_worker`, `_load_conversation`의 `conversation_switch` 취소. 대화 id마다 워커·점유·부분 응답을 둔다.            |
| 아이리스 → Hermes 호출 | 2단계만. `HermesChatWorker`가 매 턴 `set_inference_model`(`scope: main`)로 런타임 기본 모델을 통째로 바꾼다. 채팅마다 모델이 다를 때 이 전역 쓰기를 요청 단위로 바꾼다. 1단계(같은 모델, 동시 2개)는 그대로 둬도 된다. |
| Hermes 게이트웨이     | 프로세스 하나를 그대로 쓴다. 기동·재시작·포트 진단을 여러 게이트웨이로 쪼개지 않는다.                                                                                                        |
| Hermes 자체        | 소스·루프·도구 구현을 고치지 않는다. 아래 공개 API가 이미 동시 실행과 세션을 받는다.                                                                                                      |
| `iris/core`      | 손대지 않는다. 스케줄이 여기 없다.                                                                                                                                     |


아이리스가 지금 보내는 `POST /v1/chat/completions`의 `model`만으로는 요청 단위 모델이 되지 않는다. 공개 API 서버 문서는 `provider` 없는 `model`을 기본으로 무시하고, 게이트웨이 기본 모델로 떨어뜨린다. `provider`를 같이 보내거나, 세션 채팅·`/v1/runs`를 써야 그 요청의 모델이 적용된다. `direct_model_requests: true`는 그 무시를 끄는 설정이지, 아이리스가 전역 `set_inference_model`을 계속 호출해도 되는 이유는 아니다.

설치본 게이트웨이가 아래 헤더·상한을 실제로 광고하는지는 작업 전에 `/v1/capabilities`와 `gateway.api_server.max_concurrent_runs`로 확인한다. 문서 기준으로 기본 동시 실행 상한은 10이고, 넘으면 HTTP 429다. 아이리스 권고(동시 2 또는 3)는 그 안에 있다.
