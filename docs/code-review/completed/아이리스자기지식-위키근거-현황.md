# 아이리스 자기 지식 — 위키에 있어도 답은 그 노트를 안 본다

| 항목 | 내용 |
|---|---|
| 문서 번호 | IRIS-REV-2026-1003-01 |
| 작성일 | 2026-10-03 |
| 대상 | 사용자가 아이리스 구조·커스텀을 물을 때, 위키의 아이리스 노트가 답의 근거가 되는지 |
| 목적 | 「아이리스에 관한 내용을 위키에 두면 환각 대신 그 내용으로 답한다」가 코드에서 성립하는지 |
| 조사 범위 | `obsidian-vault/코드`, 코드 노트 생성, 채팅 전 노트 검색, `wiki.search` / `wiki.read_note`, 시스템 문구 |
| 하지 않은 일 | 코드 수정, 모델 호출, 사용자 DB의 실제 답변 로그 대조 |

---

## 1. 결론

그 목적은 지금 경로로는 되지 않는다. 아이리스 소스에서 구운 노트는 위키 **화면**(목록·그래프)에만 있고, 채팅이 답을 만들기 전에 넣는 검색에는 없다.

사용자가 「타일 비율이 어떻게 되지」, 「이 화면을 어떻게 고치지」라고 물으면, 앱은 `~/.iris-light/iris-wiki`의 사용자 노트(inbox, 사용자, 학습자료, 인사이트, projects, research, traits)만 찾는다. `obsidian-vault/코드/`와 `obsidian-vault/Iris Light/`는 그 색인 밖이다. 검색이 비면 「위키에 없으면 없다고 해라」는 문장도 프롬프트에 들어가지 않는다. 모델은 가중치와 시스템 문구로 답을 쓰고, 그 답이 노트와 같은지는 검사하지 않는다.

노트를 색인에 넣어도 내용이 부족하다. 생성기는 모듈 docstring **첫 줄**과 최상위 이름, import 링크만 적는다. 함수 본문, `.cursor/rules`의 계약, `docs/code-review`는 들어가지 않는다. 앱이 이 스크립트를 실행 중에 다시 부르지도 않는다. 그래서 노트는 소스보다 옛 문장으로 남을 수 있다.

---

## 2. 확인한 사실

### 2.1 아이리스 노트는 프로젝트 볼트에 있다

`scripts/generate_code_docs.py`가 `iris/**/*.py`를 `obsidian-vault/코드/<패키지>/<모듈>.md`로 쓴다. 실행할 때마다 그 폴더를 지우고 다시 만든다. 런타임(`iris/` 안의 기동·채팅)은 이 스크립트를 호출하지 않는다. 언급은 `code_index.py` 주석뿐이다.

노트 한 장의 본문은 세 덩어리다.

- 제목, 소스 상대 경로
- docstring 첫 줄. 없으면 「설명 없음」
- 최상위 class/def 이름, 아이리스 내부 import를 `[[노트]]`로

`obsidian-vault/Iris Light/프로젝트 개요.md`는 2026-08-25 생성본이다. 폴더 설명은 있으나 지금 타일·위키 검색 계약은 없다.

### 2.2 화면과 채팅 검색이 다른 저장소를 본다

| | 위키 화면 | 채팅에 붙는 노트 |
|---|---|---|
| 뿌리 | `obsidian-vault` (`docs/…`) + `~/.iris-light/iris-wiki` (`user/…`) | `user_root`만 |
| 아이리스 코드 노트 | `list_notes()`에 `docs/코드/…`로 포함 | `KNOWLEDGE_PREFIXES`에 없음 |
| `user/IRIS/` | 지금 모델·Hermes·루틴 한 장 | 색인 제외. 주석이 history·learning·schedule·IRIS를 뺀다고 적음 |

`wiki_places.py`의 색인 접두사는 `inbox/`, `사용자/`, `학습자료/`, `인사이트/`, `projects/`, `research/`와 `profile/traits.md`뿐이다.

### 2.3 노트가 현재 소스와 다르다

`iris/system/ide_tiler.py` docstring 첫 줄은 「80:20 타일 배치」이고, 이어서 PyQt는 `setGeometry`만 쓴다는 계약이 있다.

같은 파일로 구워 둔 `obsidian-vault/코드/system/ide_tiler.md` 첫 설명은 「70:30 타일 배치」이다. 계약 문단은 노트에 없다. 생성기가 첫 줄만 남기고, 그 뒤 소스가 바뀐 채로 스크립트를 다시 돌리지 않은 상태다.

이 한 장만 봐도, 위키를 근거로 삼아도 지금 앱과 다른 비율을 말할 수 있다.

### 2.4 채팅이 노트를 넣는 양

4자 이상인 질문만 검색한다. 최대 3건, 노트당 본문 **앞** 800자, 합 2400자다. 질문과 겹치는 문단을 자르지 않고 파일 앞부분을 자른다. 0건이면 블록 문자열이 빈다. 헤더의 「발췌에 있는 문장만 저장된 사실로 써라」는 그때 같이 사라진다.

3초 안에 임베딩 검색이 안 끝나면 키워드 결과만 싣는다.

나온 답에 발췌 밖 문장이 있는지는 보지 않는다. 이 점은 `답변근거강제-환각감소-현황과-개선안.md`(2026-10-02)와 같다. 이번 글은 그 다음이다. **아이리스 구조 노트는 그 발췌 후보에 들어가 있지 않다.**

## 3. 구조

「아이리스는 어떻게 짜여 있어 / 여기를 어떻게 바꾸지」가 디스크와 답까지 가는 길이다. 이번 목적(코드 노트를 근거로 답하기)은 `wiki_prompt_for_query`에서 갈라져 빠진다.

```text
사용자 문장
└─ MainWindow 채팅 전송
   └─ _with_past_chats
      ├─ 4자 미만 ─► 검색 없이 _launch_chat_turn
      └─ 4자 이상 ─► PastChatsWorker (상한 3초)
         ├─ 이전 대화 History (설정이 켜진 경우만)
         └─ wiki_prompt_for_query
            └─ sync_knowledge_notes
               └─ iter_knowledge_files
                  ├─ ~/.iris-light/iris-wiki 의 사용자 지식 폴더만 색인
                  └─ obsidian-vault/코드 · Iris Light  ← 여기로 안 감  ★
            └─ search_notes → 앞 800자 × 최대 3
               └─ 0건이면 ""
   └─ _chat_messages_with_project_context
      ├─ 시스템 문구 (도구 이름·사용법. 위키에서 읽지 않음)
      ├─ traits.md 가 있으면 짧은 블록
      ├─ 위키 발췌 (있을 때만)
      └─ 이전 대화 블록
   └─ Hermes 또는 Ollama
      ├─ 모델이 고르면 wiki.search → 같은 사용자 색인만
      ├─ 모델이 고르면 wiki.list_notes / wiki.read_note
      │    └─ docs/ 경로면 볼트 파일을 읽을 수는 있음 (강제 아님)
      └─ 최종 문장
         └─ 발췌·코드 노트와 대조하는 단계 없음  ★

따로 있는 저장 (채팅과 이어지지 않음)
scripts/generate_code_docs.py
└─ IrisCodeIndex (docstring 첫 줄, 심볼, import)
   └─ obsidian-vault/코드/*.md
      └─ IrisWiki.list_notes → 위키 화면·그래프
         └─ wiki_notes 테이블로는 안 감  ★
```

`user/IRIS/index.md`는 설정이 바뀔 때 모델 이름·Hermes 여부·루틴을 적는다. 소스 구조 노트가 아니다. 그것도 채팅 색인 밖이다.

## 4. 코드 리뷰

### 4.1 `scripts/generate_code_docs.py`, `iris/knowledge/code_index.py`

소스를 노트로 굽는 자리다. `_parse`가 docstring을 첫 줄에서 자른다. `_render`는 그 줄과 심볼·위키링크만 쓴다. 구현, 인자, `.cursor/rules`는 노트에 없다.

앱 기동이 이 스크립트를 부르지 않으므로, 소스가 바뀌어도 `코드/*.md`는 마지막 실행본이다. `ide_tiler.md`의 70:30이 그 결과다.

이 함수가 하는 일은 화면용 목차다. 채팅 근거를 만드는 일은 하지 않는다.

### 4.2 `iris/knowledge/iris_wiki.py` `list_notes` / `read_note`

`list_notes`는 볼트와 사용자 위키를 합쳐 `docs/`, `user/`로 돌려준다. 위키 화면은 이 목록을 그린다. 그래서 「위키에 아이리스가 다 있다」처럼 보인다.

`read_note`는 `docs/`로 시작하면 볼트 파일을 읽는다. 모델이 경로를 이미 알고 `wiki.read_note`를 부르면 그 얇은 노트를 받을 수 있다. 질문만으로 이 함수가 먼저 실행되지는 않는다.

### 4.3 `iris/knowledge/wiki_places.py` `KNOWLEDGE_PREFIXES`

채팅 색인이 볼 폴더를 여기서 정한다. `코드`, `Iris Light`, `IRIS`, `history`가 없다. 주석이 IRIS를 뺀다고 명시한다. 자기 구조 질문을 위한 자리가 이 목록에 없다.

### 4.4 `iris/knowledge/wiki_note_index.py` `sync_knowledge_notes`, `search_notes`, `wiki_prompt_for_query`

`iter_knowledge_files`가 위 접두사만 걷는다. `search_notes`의 발췌는 본문 앞 800자다. 질문 근처 문단이 아니다. `format_note_prompt`는 히트가 없으면 `""`를 반환한다. 지시문도 없다.

코드 노트를 이 테이블에 넣는 분기가 없다.

### 4.5 `iris/ui/window/main_window.py` `_with_past_chats`, `_chat_messages_with_project_context`

질문 직전에 위키 블록을 만든다. 블록은 `_pending_wiki_notes`로 사용자 메시지 앞에 실린다. 시스템 문구는 도구 사용을 길게 적지만, `obsidian-vault/코드`를 읽으라는 문장은 없다. 「저장된 노트는 `wiki.search`」라고만 한다. 그 검색은 4.4와 같은 사용자 색인이다.

시스템 문구의 「위키 발췌에 없는 내용을 위키에 있는 사실처럼 말하지 말 것」은, 발췌가 비어 있으면 아이리스 구조 답을 막지 못한다. 가중치로 설명해도 그 문장에 걸리지 않는다.

### 4.6 `iris/ui/workers/past_chats_worker.py`

이전 대화 임베딩과 노트 검색을 같은 3초 안에 한다. 넘기면 노트는 키워드만이다. 코드 볼트는 어느 쪽이든 대상이 아니다.

### 4.7 `iris/ui/control_actions/wiki.py` `wiki_search`, `wiki_list`, `wiki_read`

`wiki.search`는 `sync_knowledge_notes` 후 `search_notes`다. 반환 경로에 `user/`를 붙인다. 코드 노트는 히트가 될 수 없다.

`wiki.list_notes`는 볼트 포함 전체 목록이다. 노트 수가 수백이라, 모델이 부르더라도 구조 답을 그 목록에서 조립하는 절차는 없다. `wiki.read_note`는 경로가 맞으면 본문을 준다. 둘 다 모델이 선택할 때만 돈다. 선택하지 않아도 답은 나간다.

### 4.8 `iris/knowledge/iris_state.py`

`user/IRIS/`에 지금 설정과 루틴을 적는다. 「아이리스가 무엇을 하기로 했는지」용이다. 소스 구조·커스텀 방법이 아니다. 색인 제외라 채팅이 이 파일도 자동으로 안 넣는다.

### 4.9 하지 않은 일

- 답변 문장을 발췌와 맞추는 게이트 (`file_write_claim`은 파일 쓰기 문구만 본다)
- `.cursor/rules`, `docs/code-review`를 위키 색인에 넣는 일
- 생성 노트를 소스 mtime과 맞추는 일
- 이번 조사에서 실제 채팅 로그가 코드 노트를 인용했는지 DB 대조

## 5. 개선안

빈 자리는 세 곳이다. 새 검색 엔진은 필요 없다.

1. **채팅 검색이 볼트 `코드/`(와 구조 개요)를 보게 한다.** 지금 사용자 지식 색인과 테이블을 나누고, 질문 블록 제목도 나눈다. 「저장된 자료」와 「아이리스 소스 노트」가 한 발췌로 섞이면 안 된다. `wiki.search`도 같은 색인을 연다. 화면 목록만 있고 프롬프트에 없는 상태가 이 자리다.
2. **노트에 계약 본문을 넣거나, 없을 때는 소스 docstring 전체를 읽게 한다.** 첫 줄만 둔 채 색인하면 `ide_tiler`처럼 70:30을 사실로 싣는다. 생성은 앱이 소스보다 노트가 오래됐을 때 다시 하거나, 채팅은 노트 대신 해당 `.py` docstring을 `wiki.read_note`와 같은 절차로 넣는다. 규칙 파일 전문을 매 턴 넣지는 않는다. 질문과 겹치는 모듈만, 지금과 같은 3건·길이 상한이다.
3. **0건과 어긋난 답을 남기지 않는다.** 구조·커스텀 질문인데 코드 노트가 0건이면 그 사실을 블록으로 넣는다. 발췌가 있으면 비율·경로·함수명처럼 노트에 있는 토큰만 사실로 두고, 발췌에 없는 숫자는 「노트에 없다」로 바꾼다. 이미 적힌 근거 강제 개선의 위키 항과 같다. 대상만 사용자 노트가 아니라 아이리스 구조 노트로 넓힌다.

하지 말 것: 볼트 전문을 매 턴 넣기, 시스템 문구에 구조 설명을 더 써서 위키 대신 쓰기, 70:30이 남은 노트를 그대로 근거로 올리기.
