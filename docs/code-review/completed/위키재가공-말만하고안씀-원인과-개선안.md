## 1. 결론

첫 저장이 빠른 이유는 모델을 부르지 않기 때문이다. 「위키」와 「저장」과 주소가 한 문장에 있으면 Iris가 `import_to_wiki`를 바로 실행하고, 답은 도구 결과로 만든다.

그 다음 「원문은 남기고 위에 정리, 문단마다 한국어」는 이 분기에 들어오지 않는다. 주소가 없고, 문장에 「위키」가 없다. 요청은 Gemma(Hermes)의 도구 루프로 가고, 모델은 정리했다고 말한다. 노트 파일은 바뀌지 않았다.

고칠 자리는 스킬 문장이나 에이전트 프레임워크가 아니다. 이 요청은 정해진 절차다. 읽기, 요약, 문단 번역, 같은 경로에 쓰기, 열기까지 Iris가 하고, 채팅 문장은 그 결과만 보여 주면 된다. 지금 코드 쓰기 환각을 막는 방식과 같다.

## 3. 원인



### 3.1 빠른 저장과 느린 수정이 다른 길을 탄다

`_try_local_wiki_save`는 모델보다 먼저 실행된다. 조건은 `wiki_save_intent.parse_wiki_save_request`다.

- 「위키」 계열과 「저장」 계열이 같이 있어야 한다.
- 주소, 첨부, 또는 디스크에 있는 파일 경로가 있어야 한다.
- 「요약·정리·핵심」이 있으면 `summarize`, 없으면 `raw`.

첫 문장은 이 조건에 맞다. raw는 `import_to_wiki` 한 번이고, 성공 문구는 `_wiki_import_success_message`가 경로와 모드를 넣어 만든다. 그래서 빠르고, 말한 것과 파일이 같다.

세 번째 문장에는 「저장한」은 있으나 「위키」가 없고 주소도 없다. 파서는 `None`을 반환한다. 로컬 저장은 돌지 않는다.

### 3.2 있어도 지금 요약 모드는 요청과 다르다

`mode=summarize`는 `summarize_for_wiki` 결과로 본문을 바꾼다. 원문을 아래에 남기지 않는다. 입력은 24,000자에서 잘린다. 문단 아래 번역을 붙이는 동작은 없다.

사용자가 원한 형태(위 요약, 아래 원문, 문단마다 한국어)를 만드는 함수는 없다.

### 3.3 모델에게 맡기면 한 번에 못 쓴다

위키 컨트롤은 목록, 열기, 새로고침, 쓰기, 추출, 가져오기뿐이다. 노트 본문을 돌려주는 액션은 없다. 터미널 도구는 꺼져 있다. 모델은 방금 저장한 파일을 읽지 못한다.

수정은 `wiki.write_user_note`에 제목과 본문 전체를 넣어 덮어쓰는 길뿐이다. 2만 자 원문에 요약과 문단 번역을 얹으면 도구 인자 한 번으로 나가지 않는다. Gemma는 그 자리에서 최종 문장을 내고, Hermes 도구 루프는 그 문장에서 끝난다.

스킬 `iris-wiki`와 시스템 문구는 이미 「ok 없이 저장했다고 말하지 마라」고 적혀 있다. 이번 답은 그 문구를 따르지 않았다. 문장을 더 넣는 것으로는 줄지 않는다. IDE 파일 쓰기에서 같은 결론이 있다.

### 3.4 말한 완료를 걸러내지 않는다

`_gate_chat_completion`은 IDE 코드 문구만 본다. 「처리 완료」, 「작성했습니다」, 「파일을 열었습니다」. 「덮어씌웠습니다」, 「정리했습니다」, 「열어 드리겠습니다」는 통과한다.

턴 감독(`decide_followthrough`)이 저장 완료를 의심하는 경우는 목표에 「위키」와 「저장·가져오」가 같이 있고, 도구 성공이 0이며, 답에 「저장했」 계열이 있을 때다. 세 번째 목표에는 「위키」가 없다. 「덮어씌웠」은 「저장했」에 안 걸린다. 네 번째 「열어」도 감독 밖이다. 그래서 거짓 완료 뒤에 자동으로 다시 시도하지 않는다.

도구 성공 카운트도 비어 있다. `counts_as_tool_ok`는  `ok`가 있는 줄만 센다. Hermes 진행은 `_format_tool_progress`가 `status`를 `tool`보다 먼저 집어 `running`/`completed`만 남긴다. 도구를 돌려도 감독은 성공이 없다고 본다. 이름도 없어 나중에 어떤 도구였는지 로그로 확인할 수 없다.

## 4. 이번 말 외에 같은 계통의 문제

1. **원문 품질.** 주소 추출은 표준 라이브러리 HTML 파서다. 메뉴·건너뛰기 링크가 본문에 들어간다. Firecrawl은 키가 있을 때만 빈 본문의 대체이고, 이번 저장은 키가 없어도 본문이 있어 표준 파서 결과가 그대로 남았다.
2. **요약 저장은 원문을 지운다.** 「정리해서 위키에 저장」은 로컬 분기가 잡지만, 결과는 요약만 있는 노트다. 「없애지 말고」와 맞지 않는다.
3. **후속 수정은 대상을 잃는다.** 직전 `rel_path`를 세션이 기억하지 않는다. 다음 문장에 주소가 없으면 어느 노트를 고칠지 앱이 정하지 못한다.
4. **열기만 부탁해도 모델 차례다.** `wiki.open_note`는 있다. 「정리된 노트 열어」를 앱이 먼저 처리하지 않아, 이번처럼 도구 없이 문장만 나올 수 있다.
5. **긴 저장과 같은 종료.** 모델이 최종 문장을 내면 그 요청의 도구 반복은 끝이다. 일괄 저장용 감독은 「이어서」와 「위키+저장」에만 좁다. 정리·번역·열기는 빠진다.
6. **쓰기 환각 게이트와 위키가 분리.** 코드 파일은 「채팅에만 있고 파일은 없다」로 바꿀 수 있다. 위키 완료 문장은 그대로 말한다.

## 5. 개선안

한 번에 넣을 것은 아래 세 가지다. 새 에이전트 런타임은 넣지 않는다.

1. **재가공은 앱 절차로 고정한다.** 직전 저장 경로를 기억한다. 「원문 유지 + 위에 정리 + 문단 번역」이면 모델의 계획 턴을 열지 않는다. 순서: 노트 읽기 → 기존 `summarize_for_wiki`로 한국어 요약 → 문단을 잘라 번역 호출 → 요약, 원문, 문단 번역 순으로 같은 `rel_path`에 `write_inbox_note` → `wiki.open_note`. 채팅에는 반환된 경로만 적는다.
2. **위키 완료 문장을 파일로 확인한다.** 「저장·정리·덮어·번역해 두었·열었」인데 이번 턴에 쓰기 ok와 파일 변경이 없으면, 그 문장을 보여 주지 않고 「노트는 그대로다」만 남긴다. 열기만 요청한 경우는 `wiki.open_note` ok일 때만 「열었다」고 한다.
3. **도구 진행에 이름을 남긴다.** `status`만 집지 말고 액션 이름을 로그에 둔다.  `ok`가 있는 줄만 성공으로 센다. 감독이 보는 목표에 정리·번역·열기를 넣고, 성공이 0인데 완료만 말하면 상한 안에서 한 번 더 절차를 돌린다.

이미 있는 `wiki.import_content` raw 경로는 유지한다. 첫 저장이 빠른 이유를 없애지 않는다.

## 6. 말→동작은 휴리스틱이다

위키 저장은 모델이 의도를 분류하지 않는다. `wiki_save_intent`가 문장을 소문자로 만든 뒤, 미리 적은 낱말이 들어 있는지만 본다.


| 묶음  | 낱말                                        | 역할              |
| --- | ----------------------------------------- | --------------- |
| 위키  | 위키, wiki, 옵시디언, obsidian, iris wiki       | 있어야 저장 분기       |
| 저장  | 저장, 넣어, 남겨, 기록, 캡처, 보관, save, import 등    | 있어야 저장 분기       |
| 정리  | 요약, 정리, 핵심, summarize, summary, brief, 개요 | 있으면 본문을 요약으로 교체 |


둘 다 있고 주소·첨부·파일이 있으면 모델을 건너뛴다. 「정리」가 없으면 raw다. 이번 첫 문장이 이 경우다.

부분 문자열이라 「저장한」도 「저장」으로 잡힌다. 세 번째 문장은 그래서 저장 낱말은 있었지만 「위키」가 없어 분기 밖이었다. 같은 방식은 빼먹기(위키를 안 씀)와 잘못 잡기(정리·저장이 다른 뜻)가 둘 다 있다.

같은 종류의 분기는 더 있다. 공통점은 문장 형태를 코드가 미리 정해 둔다는 것이다. 모델 분류가 아니다.


| 위치                             | 보는 것                                              | 하는 일                     |
| ------------------------------ | ------------------------------------------------- | ------------------------ |
| `_try_local_ide_control`       | 문장 전체가 IDE 켜기/끄기 패턴                               | Companion 전환. 모델 없음      |
| `_try_local_workspace_control` | 문장 전체가 홈, 마이크, 메일, 캘린더, 위키 화면                     | 아이콘과 같은 전환. 모델 없음        |
| `voice_intents`                | 통화·알림 문구. 완전 일치, 포함, 낱말 묶음, 비슷한 발음                | 음성 명령                    |
| `decide_followthrough`         | 목표·답에 「전부」「계속할까요」「저장했」 등                          | 다음 턴을 넣을지                |
| `file_write_claim`             | 「작성·넣어·써·스크립트·코드」와 이미지 첨부. 완료 문구는 「처리 완료·작성했습니다」만 | 사진의 코드를 파일에 넣기, 거짓 완료 삭제 |


IDE·화면 전환은 문장 전체를 맞춘다. 길면 모델로 넘어가서, 위키 저장보다 잘못 실행은 적다. 위키 저장과 턴 감독은 낱말 포함이라 이번처럼 빠지거나, 다른 뜻의 「정리」에 걸린다.

검색용 FTS, HTML 파서, 사용량 화면 정규식은 말을 동작으로 바꾸는 분기가 아니라 여기 넣지 않았다.

## 7. 확인 방법

재현 문장 세 개로 본다.

1. 주소와 「위키에 저장」: 지금처럼 raw 노트가 생기고, 답에 경로와 `raw`가 있다.
2. 직후 「원문은 남기고 위에 정리, 문단 아래 한국어」: 같은 파일이 바뀌고, 위에 한국어 요약, 아래에 원문과 문단 번역이 있다. 채팅의 경로가 그 파일과 같다.
3. 파일을 일부러 안 쓰고 모델이 「정리했습니다」만 내게 한 경우: 그 문장은 화면에 없고, 「노트는 그대로다」만 남는다.
