# 위키 기능 — 키워드 휴리스틱인가

| 항목 | 내용 |
|---|---|
| 문서 번호 | IRIS-REV-2026-1003-02 |
| 작성일 | 2026-10-03 |
| 대상 | `docs/code-review/위키폴더이동-노트미지정-원인.md`를 보고, 위키 기능 전체가 키워드 휴리스틱인지 |
| 목적 | 문장 가로채기·폴더 배정·검색·도구·완료 문장이 각각 무엇을 보는지 구분 |
| 조사 범위 | `parse_wiki_command`, `wiki_save_intent`, `classify_note`, `search_notes`, 위키 액션 카탈로그, 완료 게이트 |
| 하지 않은 일 | 코드 수정, 위키 파일 변경 |

관련: `docs/code-review/위키폴더이동-노트미지정-원인.md` (같은 날). 그 문서는 한 문장이 삭제로 끊긴 경로만 다룬다. 이 문서는 그 파서가 위키 전체인지 본다.

---

## 1. 결론

채팅 문장을 위키 명령으로 바꾸는 입구는 키워드 부분 문자열이다. Hermes가 켜져 있어도 이 입구는 모델보다 먼저 탄다. 맞은 명령이 있으면 그 턴은 도구 루프로 내려가지 않는다.

위키 전부가 그 방식은 아니다. 노트를 어느 폴더에 둘지는 임베딩 코사인이고, 애매할 때만 모델 JSON이다. 저장된 노트를 찾는 `wiki.search`는 FTS와 임베딩을 섞는다. 모델이 고르는 `wiki.write_user_note` 같은 도구는 인자 구조이지, 사용자 문장의 단어 목록이 아니다. 그 도구에 도달하려면 키워드 파서가 먼저 `None`을 내야 한다.

폴더를 만들거나 옮기는 동작은 키워드 목록에도, 도구 카탈로그에도 없다.

---

## 2. 구조

같은 「위키」 요청이 세 갈래로 갈라진다.

```
사용자 문장
        │
        ▼
_execute_user_turn
  try_wiki_command          ← Hermes 여부와 무관. 항상 먼저
        │
        ├─ parse_wiki_command 가 WikiCommand 를 만들면
        │     execute_wiki_command 후 return
        │     모델·도구 루프는 이 턴에 없음
        │     명령 종류는 단어 포함 검사
        │
        └─ None 이면
              Hermes 켜짐 → 모델이 iris_invoke 로 도구 선택
              Hermes 꺼짐 → _try_local_wiki_save (또 단어 목록)
                            그다음 PDF·IDE 등
        │
        ▼  (저장이 실제로 일어날 때)
file_user_note
  rel_path 가 있으면 그 경로
  없으면 classify_note
        임베딩 코사인 → 바닥·간격 미달이면 inbox
        임베딩 실패·분야 이름만 모델 JSON
        │
        ▼  (모델 답이 나온 뒤, 로컬 명령 턴은 여기까지 안 옴)
_gate_chat_completion
  wiki_work_goal 이 단어로 위키 작업인지 보고
  답에 「저장했」 등이 있는데 이번 턴 쓰기가 없으면 「노트는 그대로다」
```

`hermes_owns_local_intents`는 IDE·화면·위키 저장·PDF·확장의 **두 번째** 가로채기를 끈다. `try_wiki_command`는 그 분기 위에 있어서 꺼지지 않는다.

---

## 3. 확인한 사실

### 3.1 문장 → 명령은 단어 포함

`iris/knowledge/wiki_command.py`는 형태소·의도 분류 모델이 없다. `_norm`으로 공백을 접고 소문자로 만든 뒤, 튜플 안 문자열이 들어 있는지로 동작(op)을 고른다. 먼저 맞은 분기가 반환이라 뒷문장은 안 읽는다.

| 함수 | 보는 문자열 | 만드는 op |
|---|---|---|
| `_wants_delete` + `_delete_context` | 삭제·지워·없애·delete, 그리고 위키·노트·문서·wiki | `delete` (맨 앞) |
| `_wants_list` | 목록·리스트·list + 위키·노트 | `list` |
| `_wants_open_note` | 열어·보여·open + 노트·문서·방금 | `open` |
| `_wants_create` | 만들·생성·작성 + 「새 노트」 등 | `create` |
| `is_wiki_save_intent` | 위키 계열 + 저장·넣어·남겨·기록… , URL·파일 있음 | `save` |
| 대상 경로가 있을 때 | 바꿔·수정·제목 / 원문·문단·요약 | `update` 또는 `reprocess` |

예외는 부분 문자열을 또 빼는 정도다. 「없애지」「지우지」「삭제하지」는 삭제가 아니고, 「코드」「함수」「버그」가 있으면 재가공으로 안 본다. 「위키 화면 열어」는 정규식 `_SCREEN_OPEN` 전체 일치일 때만 명령이 아니다.

플래그도 같다. `_wants_summary`는 「요약」「정리」「핵심」「개요」. `_wants_translate`는 「번역」「한국어」「문단」. 「문단」만 있어도 번역으로 본다.

출처가 없을 때의 저장은 `wiki_save_intent.parse_wiki_save_request`다. 「방금 답변을 위키에 저장」처럼 **문장 전체**가 한 정규식에 맞을 때만 직전 비서 답을 넣는다. 그 외 연구·조사 요청은 `None`이라 모델로 간다.

### 3.2 폴더 배정은 단어 목록이 아니다

`wiki_classify.py` 모듈 주석: 「점수는 임베딩 코사인이다. 본문 단어 목록으로 폴더를 고르지 않는다.」 `wiki_filing.open_classifier` 주석: 「키워드 대체는 없다.」

`wiki_places.PLACES`의 `prototype`은 「학습자료」「인사이트」 같은 폴더를 고르는 **비교 문장**이다. 본문에 그 단어가 있는지로 폴더를 찍지 않는다. 코사인이 `PLACE_FLOOR`(0.45) 미만이거나 1·2위 차가 `PLACE_MARGIN`(0.04)보다 좁으면 `inbox`다. 임베딩이 없거나 호출이 실패하면 `_from_model`이 place id와 분야 이름을 JSON으로 받는다. 분야 이름은 `clean_field_name`이 슬러그로만 자른다.

그래서 「강화학습 폴더를 만들어 옮겨」는 분류기가 받는 종류의 문장이 아니다. 분류기는 이미 쓰기로 결정된 노트 본문을 기존 장소 중 하나에 붙인다.

### 3.3 검색·도구·완료 문장

`wiki.search` → `search_notes`는 SQLite FTS `MATCH`와 노트 벡터 코사인을 RRF로 합친다. 질의 단어를 쓰지만, 채팅 의도를 나누는 목록은 아니다. 카탈로그에 있고, 파서가 `None`인 턴에서만 모델이 호출한다.

`action_catalog.json`의 위키 액션은 `list_notes`, `open_note`, `reload`, `search`, `write_user_note`, `import_content`, `import_pages`다. 핸들러는 인자(`rel_path`, `title`, `content`, `source`)를 받는다. 사용자 문장을 다시 단어로 쪼개지 않는다. `delete_note` 핸들러는 `iris/ui/control_actions/wiki.py`에 있으나 카탈로그에 없다. 폴더 생성·이동·이름 변경 함수는 `iris/`에 없다. 그래프의 드래그는 화면 좌표만 바꾼다 (`wiki_graph_view._drag_moved`).

완료 문장만 다시 키워드다. `wiki_claim.wiki_work_goal`은 목표에 「위키」와 「저장·정리·삭제·만들」 등이 같이 있으면 위키 작업으로 본다. `settle_wiki_claim`은 답의 「저장했|정리했|삭제했」를 이번 턴의 `wrote`와 맞춘다. `turn_followthrough._wiki_save_goal`은 같은 `wiki_work_goal`을 쓴다. 로컬 파서가 턴을 끝내면 이 검사는 모델 답에 안 붙는다.

노트 하나를 고르는 `match_wiki_notes`는 제목·경로·폴더에 힌트 문자열이 포함되는지로 거른다. 의도 분류는 아니고, 삭제·열기에서 경로가 비었을 때의 이름 찾기이다.

### 3.4 Hermes가 켜져도 파서는 먼저다

`agent_local_gate.hermes_owns_local_intents` 주석은 「위키·PDF의 신규 가로채기를 하지 않는다」이다. `_execute_user_turn`에서 그 값이 참이면 `_try_local_wiki_save`와 `_try_local_pdf_save`는 건너뛴다. 그 두 함수도 단어 목록이다 (`is_wiki_save_intent`, `is_pdf_save_intent`). PDF 쪽은 문장에 위키 단어가 있으면 PDF로 보지 않는다.

`try_wiki_command`는 이 분기 **앞**이다. Hermes가 켜진 채팅도 `parse_wiki_command`가 명령을 만들면 모델에 안 간다. 폴더 이동 보고서의 실패는 이 줄이다.

## 4. 코드 리뷰

### 4.1 가로채기 — 키워드가 맞다

`main_window._execute_user_turn`은 Hermes 소유 여부를 보기 전에 `try_wiki_command`를 호출하고, 참이면 `return`한다.

`wiki_turn.try_wiki_command`는 `parse_wiki_command` 결과만 본다. `None`이 아니면 사용자 문장을 에코하고 `_start`로 실행한다. 계획 턴을 열지 않는다고 모듈 주석에 적혀 있다.

`parse_wiki_command` 184행은 삭제 조건이 참이면 즉시 `op="delete"`를 반환한다. 폴더·여러 파일·「옮겨」는 이 함수의 op에 없다. `create`는 「새 노트」 한 장이다.

이번 질문에서 이 경로가 한 일: 위키로 들리는 문장을 모델이 보기 전에 닫을 수 있다. 막지 못한 이유: 포함 검사는 문장 앞의 동사 하나와 「위키」만으로 참이 되고, 나머지 절을 볼 자리가 없다.

### 4.2 분류·검색 — 키워드 의도가 아니다

`classify_note`는 노트 벡터와 장소 프로토타입·기존 폴더 벡터의 코사인으로 place를 고른다. 단어 목록 분기는 없다. 임베더가 없으면 모델 JSON이다. 둘 다 실패에 가깝게 비면 `Decision("inbox", "", True)`다.

`search_notes`의 `_keyword_ids`는 FTS `bm25`다. `_vector_ids`는 임베딩이다. 둘을 합쳐 발췌를 돌려준다. 채팅 op를 만들지 않는다.

이번 증상의 폴더 이동에는 둘 다 호출되지 않았다. 파서가 턴을 닫기 때문이다.

### 4.3 도구·완료 게이트 — 파서 뒤에만 의미 있다

카탈로그 도구는 모델이 이름과 인자를 고른다. 사용자 문장의 「삭제」「위키」를 다시 검사하지 않는다. 파서가 먼저 명령을 만들면 이 도구는 그 턴에 없다.

`settle_wiki_claim`과 `decide_followthrough`는 목표·답의 단어를 본다. 파일을 옮기지 않는다. 쓰기가 없었는데 완료처럼 보이면 문장만 바꾼다. 로컬 삭제 실패 문장(`위키 처리 실패: …`)은 이 검사의 「저장했」 패턴이 아니라서, 설령 도달해도 바꾸지 않는다. 이번 실패 턴은 모델 답이 없어 여기까지 오지 않는다.

### 4.4 하지 않은 일

- 위키 트리 UI의 폴더 드래그로 디스크를 옮기는 코드는 없다.
- `wiki_links.parse_wiki_links`는 `[[노트]]` 문법이다. 채팅 의도 파서가 아니다.
- 분류기 프로토타입 문장을 키워드 사전으로 세지 않았다. 임베딩 앵커다.

---

## 5. 빈 자리

키워드인 곳과 아닌 곳을 나누면, 비어 있는 것은 다음이다.

1. 채팅 입구(`parse_wiki_command`)만 단어 포함으로 op를 고정하고, Hermes보다 앞에서 턴을 닫는다. 폴더 생성·이동은 그 목록에 없다.
2. 분류·검색·도구는 그 입구를 통과한 뒤에야 쓰인다. 입구가 명령을 만들면 임베딩도 모델 도구도 그 문장을 못 본다.
3. 완료 게이트의 단어도 「위키 작업인가」와 「완료라고 했는가」만 본다. 요청한 폴더 배치와 디스크를 비교하지 않는다.
