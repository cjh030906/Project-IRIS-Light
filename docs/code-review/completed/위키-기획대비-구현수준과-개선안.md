# Iris Wiki — 기획 대비 구현 수준 · 개선안

> **작성**: 2026-10-01  
> **범위**: 사용자 기획(특성·성장 파악, 공부·개발·연구 참고/기록, RAG로 토큰 절약·환각 방지)과 현재 코드 대조. 구현은 하지 않음.  
> **기획 원문**: `obsidian-vault/Iris Light/Wiki LLM 설계.md` (2026-07-30, 이후 History RAG가 추가되어 문서보다 코드가 앞선 부분이 있음)

---

## 1. 한줄 결론

위키는 **두 저장소가 따로** 있다. 대화 원문은 History에 쌓이고 RAG도 그 원문만 본다. 사용자가 저장을 요청한 자료와 답변은 **전부 `user/inbox/` 마크다운**으로만 떨어지고, 그 파일은 검색·주입 대상이 아니다.

기획에서 기대한 **사용자 특성·성장 노트**, **공부/프로젝트/연구로 나뉜 지식**, **그 지식을 근거로 답하는 RAG**는 없다. 있는 RAG는 예전 대화를 조금 붙여 주는 수준이라, 자료 전체를 프롬프트에 넣지 않아 토큰을 아끼거나 저장된 사실로 환각을 막는 용도로는 아직 쓰이지 않는다.

## 3. 지금 실제로 있는 것

### 3.1 받는 함 — `user/inbox/`

`wiki.write_user_note`, `wiki.import_content`, `wiki.import_pages`, “방금 답변 위키에 저장”은 모두 `IrisWiki.write_inbox_note`로 간다. 기본 경로는 `inbox/{slug}.md`. 스킬(`iris-wiki`)도 ad-hoc 저장을 inbox로 안내한다.

폴더 `profile/`, `schedule/`, `learning/`, `IRIS/`, `history/`는 각각 **설정 동기화·일정·화면 조작 학습·루틴·대화 일지**용이다. 공부 자료나 연구 노트를 받는 칸이 아니다. `learning/workflows.md`는 GUI 시연 학습 목록이다.

### 3.2 대화 일지 + History RAG

매 채팅 턴은 SQLite `wiki_history`와 `history/YYYY-MM/YYYY-MM-DD.md`에 남는다. 종류는 대화·수행·생성물·입력·요약이다. 검색은 FTS5(trigram) + 선택적 Ollama 임베딩(`bge-m3`)을 RRF로 합친다.

프롬프트에 붙는 경우는 세 가지뿐이다.

- 다른 대화의 이전 기록: 최대 3건, 유사도 기준을 통과할 때만 (`past_chats`)
- 모델을 바꿨는데 원문이 컨텍스트에 안 들어갈 때 인수인계 발췌
- 예약 루틴 실행 시 과제 문장으로 History 검색

입력 종류(`kind=input`) 설정은 있으나, inbox로 저장한 PDF·URL·파일은 `record_entry`를 타지 않아 **이 색인에 안 들어간다.**

### 3.3 사람이 보는 UI

위키 화면의 검색은 제목·경로 부분 일치(`match_wiki_notes`)다. 본문 검색도, 모델 주입도 아니다. 노트 열기·목록·그래프(폴더 허브)는 된다.

## 4. 비어 있는 것

1. **사용자 모델이 없다.** 이름·취미·관심 분야는 사용자가 설정에 적은 정적 필드다. 대화에서 성격, 관심의 변화, 성장 수준을 뽑아 `profile/`에 갱신하거나 양쪽이 같이 보는 흐름이 없다.
2. **지식 노트가 RAG 밖에 있다.** inbox에 쌓인 공부·조사 자료는 파일을 직접 열지 않으면 모델이 모른다. 그래서 “저장해 둔 내용을 근거로 답하고, 없으면 모른다고 한다”가 성립하지 않는다.
3. **용도별 위치가 없다.** 자료·대화 요약·개발 결정·연구 메모가 한 inbox에 섞인다. 프로젝트별 폴더, 공부 단원, 연구 주제 링크가 없다.
4. **작업 중 추가 기록이 명시 저장에만 의존한다.** IDE에서 파일을 쓰거나 연구를 진행해도 위키 결정 노트는 늘지 않는다. 사용자가 “위키에 저장”이라고 할 때만 inbox에 떨어진다.
5. **세션 요약이 꺼져 있다.** `write_episode`가 대화 묶음을 `history/episodes/`에 넣고 색인하는 API인데, 런타임은 부르지 않는다. 성장·관심 파악의 입력이 될 요약층이 비어 있다.
6. **노트 검색 도구가 없다.** 카탈로그에 `wiki.search`가 없다. 모델은 `list_notes`로 목록을 받거나 경로를 알고 `open_note`를 연다. 설계서의 민감정보(키·주민번호) 주입 가드도 없다.
7. **그래프는 탐색용 지도가 아니다.** `[[노트]]` 연결용 맵을 만들고 반환만 한 뒤 버린다. 공부·연구 노트를 링크로 엮는 루프가 UI에 안 보인다.
8. **위키 파일을 고쳐도 검색 DB는 그대로다.** History 쪽은 마크다운이 사본이고 검색은 DB다. inbox 노트는 그 DB에도 없다.

이전 진단(`IRIS_AI_Architecture_Diagnosis.md`, 2026-09-22)의 “위키 RAG 없음”은 **노트 지식**에 대해서는 아직 맞다. **대화 History RAG**는 그 이후에 들어왔다. 둘을 같은 기능으로 보면 안 된다.

---

## 5. 개선안 (핵심만)

순서는 기획에 가까운 것부터다. 매 턴 볼트 전체를 넣지는 않는다. 설계서가 이미 그 위험을 적었다.

1. **inbox는 받는 곳만 남긴다.** 저장 직후 한 줄 분류로 `study/`, `projects/{열린 프로젝트}/`, `research/` 중 하나로 보낸다. 분류가 애매하면 inbox에 두고 사용자에게 폴더만 묻는다. 기본 경로를 항상 `inbox/{slug}.md`로 고정하는 안내(스킬·시스템 프롬프트)를 바꾼다.
2. **노트 본문을 History와 같은 FTS+임베딩에 올린다.** 채팅을 보내기 전에 질문과 겹치는 노트 Top-k(노트당 짧은 발췌, 총량 상한)만 넣는다. 이게 토큰 절약이고, “위키에 있는 문장만 사실로 쓴다”가 환각 방지다. 대화 원문 RAG와 소스를 구분해서 표시한다.
3. **특성·성장은 원문 위에 얇은 노트로 둔다.** 세션이 끝날 때 `write_episode`로 요약한 뒤, 관심사·지금 수준·이번에 나아진 점만 `profile/traits.md`에 고친다. 근거는 에피소드 링크. 사용자가 위키에서 고치면 그 파일을 짧은 블록으로 매 턴 넣는다. 성격 점수를 자동 채점하지 않는다.
4. **열린 프로젝트에서 일한 결정은 그 프로젝트 노트에 덧붙인다.** IDE `project_root`가 있으면 저장·결정 기록의 기본 위치를 `projects/{slug}/`로 한다. 모델이 필요할 때만 `wiki.search`로 연다.
5. **그래프에서 `[[링크]]`를 실제로 잇는다.** `_add_cluster`가 돌려주는 인덱스를 쓰지 않고 버리는 부분이 그 자리다.

하지 말 것: inbox에 분류 없이 계속 쌓기, 대화 전문을 매 턴 넣기, 프로필 폼 필드만 늘려 성장도로 간주하기.
