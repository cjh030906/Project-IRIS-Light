# 다중 채팅 동시 작업 구현 보고서

| 항목 | 내용 |
|---|---|
| 문서 번호 | IRIS-IMPL-2026-1002-01 |
| 작성일 | 2026-10-02 |
| 관련 | IRIS-REV-2026-0930-02 구조 검토 |
| 대상 | Iris Light 메인 채팅 실행 |
| 목적 | 채팅별 동시 작업의 구현 단계와, 헤르메스 유지 여부 |

---

## 1. 결론

구현은 아이리스 채팅 실행을 세 단계로 나눈다. 헤르메스는 일상·개발·프로젝트의 공통 에이전트와 프레임워크로 유지한다. 장기 기능 향상은 이 세션 분리가 전제이고, 헤르메스 교체는 그 향상의 조건이 아니다.

---

## 2. 구현 단계

선행 확인. 2단계 착수 전 설치본 게이트웨이의 `/v1/capabilities`와 `gateway.api_server.max_concurrent_runs`를 본다. 문서상 기본 상한은 10, 초과 시 HTTP 429이다.

### 1단계. 세션 실행

대화마다 워커, 진행 플래그, 이어하기, 부분 응답을 둔다. 채팅 전환은 화면만 바꾸고, 백그라운드 루프는 취소하지 않는다. 전송은 대화 id를 싣고, 정지 버튼은 그 채팅만 멈춘다. 동시 루프는 2개로 시작한다. IDE·파일 쓰기·터미널은 잠금 하나다. 잠금이 없으면 그 세션만 기다리고, 다른 세션의 읽기와 조사는 계속된다.

이 단계의 결과. 조사와 서류는 채팅마다 동시에 진행된다. 코딩은 한 채팅만 쓴다. 모델은 지금처럼 하나다.

완료 기준. 채팅을 옮겨도 진행 중 답이 끊기지 않는다. 두 채팅이 같은 파일을 동시에 고치지 않는다.

### 2단계. 요청 단위 모델과 프레임워크 유지

채팅마다 다른 모델을 쓸 때 연다. `set_inference_model`(`scope: main`)로 런타임 기본 모델을 바꾸지 않고, 그 요청에 `model`과 `provider`를 싣는다. `provider` 없는 `model`은 게이트웨이가 무시하고 기본 모델로 떨어뜨린다. 세션 채팅 또는 `/v1/runs`를 쓰면 요청 모델이 적용된다.

이 단계에서 프레임워크를 결정한다. 판단은 3절이다. 결정이 유지이면 2단계는 호출 방식만 바꾸고 헤르메스 소스·게이트웨이 프로세스·`iris/core`는 그대로 둔다.

완료 기준. 모델이 다른 두 채팅이 서로의 기본 모델을 덮어쓰지 않는다. 같은 게이트웨이 프로세스에서 두 런이 동시에 산다.

### 3단계. 코딩 병렬

같은 저장소를 고치는 채팅은 Git worktree 또는 동등한 사본을 빌린다. 본 트리는 한 세션만 쓴다. 터미널은 세션별 작업 디렉터리에서만 실행하고, 같은 디렉터리의 동시 실행은 금지한다. 끝나면 사용자가 본 트리로 가져온다. 자동 병합은 넣지 않는다.

완료 기준. 두 코딩 채팅이 본 작업 트리를 동시에 고치지 않는다. 가져온 결과는 사용자가 확인한 뒤에만 본 트리에 들어간다.

---

## 3. 헤르메스 적합성 (2단계 판단)

헤르메스는 일상, 개발, 프로젝트에 공통으로 적합하다. 에이전트와 프레임워크를 용도별로 나누지 않는다.

| 용도 | 지금 헤르메스가 맡는 일 | 판단 |
|---|---|---|
| 일상 | 대화, 메일·일정, 위키, 자료 조사. 도구 루프와 스킬·MCP | 적합. 세션과 기록만 나누면 병렬이 된다 |
| 개발 | IDE, 파일, 터미널. 같은 루프 위의 쓰기 도구 | 적합. 쓰기는 아이리스 잠금과 작업 사본이 경계를 만든다 |
| 프로젝트 | 저장소 수정, 긴 작업, 스킬 설치 | 적합. 본 트리 보호는 3단계 사본으로 한다 |

에이전트로서. 생각·행동·관찰은 한 궤적이고, 궤적은 세션 안에 둔다. 일상과 개발이 다른 루프를 가질 이유는 없다. 다른 점은 도구와 격리이다.

프레임워크로서. 세션, 동시 런, 요청 단위 모델, 스킬, MCP, 런 정지·승인은 헤르메스 API가 이미 제공한다. 아이리스는 화면, 대화별 실행 슬롯, 경로 잠금, worktree를 맡는다. 이 경계가 장기 기능의 자리다.

유지하는 이유. 전역 모델 덮어쓰기와 채팅 전환 시 취소는 헤르메스 한계가 아니다. 아이리스가 슬롯을 하나 두고, 매 턴 기본 모델을 통째로 바꾸기 때문이다. 교체하면 게이트웨이, 스킬, MCP, 페르소나, 설치 절차를 다시 만들고, 동시 채팅 문제는 새 런타임 위에서도 남는다.

나중에 다시 볼 조건. 설치본이 세션·동시 런·요청 단위 모델을 광고하지 않거나, 한 게이트웨이가 런 둘을 안정적으로 받지 못할 때. 그 경우에도 대상은 헤르메스 버전 정합이고, 다른 에이전트 SDK로의 이전은 본 구현의 범위 밖이다.

본 구조가 해결하지 않는 것. 근거 회수, 장기 기억, 단순 질문과 무거운 도구 경로의 분리, 소형 로컬 모델의 도구 준수. 이는 기존 구조 진단의 별도 과제이며, 프레임워크 교체의 근거로 쓰지 않는다.

---

## 4. 장기 기능 향상

세션 분리는 이후 기능의 전제로 적합하다.

| 이후 기능 | 이 구조가 주는 것 |
|---|---|
| 조사 중 다른 채팅에서 작업 | 1단계 루프 분리 |
| 채팅마다 다른 모델 | 2단계 요청 단위 모델 |
| 백그라운드 도구 승인 | 승인을 그 세션의 런에 붙임 |
| 코딩 작업 겹치기 | 3단계 작업 사본 |
| 음성 입력 | 마이크는 하나. 어느 채팅에 넣을지 규칙은 따로 정함 |

적합하지 않은 기대. 동시 루프가 로컬 추론을 두 배로 빠르게 하지는 않는다. 클라우드 한도는 채팅 수만큼 빨리 준다. 답변의 정확도와 기억은 이 구현으로 늘지 않는다.

순서. 1단계 없이 2·3단계를 열지 않는다. 3단계를 1단계와 같이 넣으면 의존성 설치와 결과 병합이 먼저 장애가 된다.

---

## 5. 조치

1. 1단계부터 구현한다. 동시 2, 쓰기 잠금 하나, 헤르메스 유지.
2. 2단계는 게이트웨이 능력 확인 뒤에 연다. 판단은 헤르메스 유지, 호출만 요청 단위로 바꾼다.
3. 3단계는 코딩을 겹쳐야 할 때 연다. 자동 병합은 제외한다.
